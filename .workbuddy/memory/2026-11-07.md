## 把本机 GPU 语音服务开放给远程阅读器（p2wlan）

用户目标：远程电脑装同一份 Free Koodo Reader，朗读时用本机的 3090 出声音。
问「能不能用原版的自建服务器」。

**结论**：不能。原版 `Dockerfile`/`docker-compose`/`httpserver`（Go）+ Caddy 提供的是
Web 版阅读界面 + 书库上传 + OPDS/KOReader 同步，**不转发 TTS**；且 Web 版没有
`window.electronAPI`，而 `ttsUtil.getAudioPath` 走的是 `electronAPI.invoke("generate-tts")`，
IndexTTS 插件在浏览器里直接失效。正确形态是「原生 Electron 客户端 + 远端 TTS 地址」。

### 服务端 `~/software/indextts_server.py`（已重写）

- 绑定 `INDEXTTS_BIND`（默认 `0.0.0.0`），端口 `INDEXTTS_PORT`
- `ThreadingHTTPServer` + `GPU_LOCK`（引擎非线程安全，3090 也只能串行）；backlog 5→64（须用子类设类属性，构造后设无效）
- `INDEXTTS_TOKEN` → `Authorization: Bearer`，`hmac.compare_digest`
- 参考音色支持 mp3/flac/m4a/ogg（ffmpeg 转 float32）→ `/voices` 从只列 wav 变成 **110 个音色**
- `format: "mp3"`（64k 单声道，**体积 1/5.4**），响应带 `X-Audio-Duration` / `X-Gen-Seconds`
- 可选 8 维 `emo` 向量 + `emoWeight`
- 新增 `POST /analyze`：服务端代理本机 Ollama 做角色分类 → **远端不必暴露 11434**
- `INDEXTTS_MAX_TEXT`（默认 2000）超出 413；`/health` 带 queue/lastRtf

启动脚本 `start_indextts.sh` 改为读 `~/.config/indextts-server.env`，默认 bind 0.0.0.0。
另写了 `~/.config/systemd/user/indextts-server.service`（未 enable）。

### 客户端

- `src/utils/reader/ttsUtil.ts`：原来 `config: voice.config` 只含 `{ref}`，插件里的
  `config.url || 127.0.0.1` 永远走默认值 —— **URL 实际改不了**。改为三层合并

  远端只配一个 TTS 地址即可。

  （设置→插件→Edit 就能填）。

### 实测

- 单实例基线 RTF **0.46**（142 字，6.05s 生成 / 13.26s 音频）
- **三实例同开时 RTF 恶化到 14.8（慢 32 倍）** —— 显存打满，这台机器只能跑一个实例
- mp3 42KB vs wav 230KB；mp3 转码开销落在噪声里
- 401 鉴权、413 超长、/analyze 返回 narrator/female/male、未知音色 400 全部验证通过
- 插件端到端：mp3 落盘后缀正确、ID3 头正确、错 token 401

### 踩到的坑（值得记）

1. **keep-alive 下 BaseHTTPRequestHandler 是同一实例服务多请求**，`_body_consumed` 标志
   跨请求残留 → 第二次请求不 drain body → 残留 body 被当下一个请求行 → 501
   `Unsupported method`。必须在 `do_GET`/`do_POST` 开头逐请求重置。
2. 错误响应（401/404）前不 drain body 同样会污染连接；经代理转发时是 **chunked**，
   没有 Content-Length，必须实现 chunked 读取。
3. 请求行可能是**绝对 URI**（代理风格），路由要用 `urlparse(path).path` 兜底。
4. 沙箱里 `pgrep -af`/`ps` 看不到宿主进程（PID namespace 隔离），
   用户手动跑的 8972 我杀不掉，只能让他自己重启。

文档：`REMOTE_TTS_SERVER.md`。

## 远程 Ollama 接入方案（只做评估，未改代码）

服务重启确认后用户问两件事：远程还需不需要 Ollama；能不能直接调本机 Ollama。

**实测结论**（`POST http://10.20.0.2:8972/analyze` 直接返回正确角色标签）：
- 多角色朗读的角色分析**已由 8972 的 /analyze 代理掉**，远程不装 Ollama 也能用，
  地址从 `ttsServerUrl` 自动推导 `/analyze`。
- AI 问书/助手（`src/utils/request/ollama.ts`，`aiLocalUrl`）与 Ollama 划词翻译
  （`catalog.ts` 里 `ollama-translate-plugin` 的 `config.url`）都直连 `127.0.0.1:11434`，
  **远程必然连不上**。
- Ollama 当前只绑 `127.0.0.1:11434`；drop-in 在
  `/etc/systemd/system/ollama.service.d/override.conf`，已设 `OLLAMA_ORIGINS=*`、
  `OLLAMA_FLASH_ATTENTION=1`、`HTTP(S)_PROXY=127.0.0.1:7892`。
- `qwen3.5:9b` 常驻 6.7 GB / 32k ctx。和 IndexTTS2 在 24 G 上能共存，
  但 27b / gemma4:26b（17 GB）会抢显存。
- p2wlan 网卡是 `p2wlan0`，`10.20.0.2/16`，MTU 1420。

**方案**：A 直接绑 0.0.0.0 + ufw 限源（零代码，有 `/api/pull` 风险）；
B 在 8972 加 `/ollama/*` 反向代理 + token（客户端填 `http://host:8972/ollama`
即可，因为 `main.js` 的 `resolveOllamaEndpoint` 只截 `/api/` 之后的部分、会保留路径前缀）；
C 独立代理进程。推荐先 A 验证再 B。

**记下的坑**：`roleAnalysisModel` 默认硬传 `qwen3.5:9b`，远端模型名对不上就
全部退化成 narrator；`/api/tags` 超时写死 5 秒；`keep_alive` 默认 5 分钟，
朗读间隔长会反复卸载模型。**8972 目前 `auth=off` 且绑 0.0.0.0，等于敞口。**

文档：`REMOTE_OLLAMA_PLAN.md`。

## ufw 规则是否误伤本机回环（查证）

用户担心 `ufw deny 11434/tcp` 会挡住本机 `/analyze` 走的 `127.0.0.1:11434`。

**结论：不会。** 三条依据已核实：
1. `/etc/ufw/before.rules` 首条 `-A ufw-before-input -i lo -j ACCEPT`，
   链路 `INPUT → ufw-before-input → ufw-user-input`，lo 在用户规则之前放行；
   `before6.rules` 同规则，`::1` 安全。
2. `ip route get 10.20.0.2` → `local 10.20.0.2 dev lo table local`，
   本机访问自己的 p2wlan 地址也走 lo。
3. `/etc/default/ufw` 已是 `DEFAULT_INPUT_POLICY="DROP"` ——
   `ufw deny 11434/tcp` 完全冗余，可以删。

**两个新发现（已写回方案文档）**：
- `ENABLED=no`，**ufw 当前根本没启用**，只跑 allow 规则不生效，必须 `ufw enable`；
  而 enable 会立刻套 DROP 默认策略，先 `ufw allow 22/tcp` 否则可能断 SSH。
- `OLLAMA_HOST=0.0.0.0` 是 IPv4 only，客户端填 `localhost` 若解析到 `::1` 会连不上，
  与防火墙无关；客户端一律填 `127.0.0.1` 或 `10.20.0.2`，双栈用 `[::]:11434`。

## 改 Ollama 绑定 / 开 ufw 的影响面（查证）

**依赖本机 Ollama 的本地程序**（已 grep 确认）：
- `~/.local/bin/rime-speech-ollama.sh` → `127.0.0.1:11434/api/generate`（语音输入润色）
- `~/.local/bin/ollama-batch` → `localhost:11434`
- `indextts_server.py` 的 `OLLAMA_URL` 默认 `127.0.0.1:11434`（/analyze）
- free-koodo-reader 的 AI 助手 / 划词翻译
- `ollama` CLI

结论：`OLLAMA_HOST=0.0.0.0` **包含 127.0.0.1**，上述全部不受影响；
唯一代价是 restart 期间请求失败 + 模型卸载（qwen3.5:9b 6.7 GB，首请求多等 3–8 秒）。

**关键发现（纠正用户判断）**：`0.0.0.0` 会同时监听校园网口
`eno1 172.21.225.12/19`（约 8000 个地址），校园网是大二层、无 NAT，
所以这个场景比家庭网络更需要按网卡挡。

**本机现有 0.0.0.0 监听端口**（ufw enable 会全部打掉）：
22 / 80 / 3306(MySQL) / 6333+6334(Qdrant) / 6099 / 5173 / 5174 /
8972(TTS) / 9002 / 15176 / 40653。其中 **8972 被打掉会直接让远程朗读失效**。

**推荐路径**：不开 ufw，只加
`sudo iptables -I INPUT -i eno1 -p tcp --dport 11434 -j DROP`，
配 oneshot unit 持久化（写进了 `REMOTE_OLLAMA_PLAN.md` 第四节）。

**Docker 会让 ufw 失效**：本机有 docker0 + br-5b4b776835ec + br-32935224fcd8
三个网桥，Docker 直写 iptables 绕开 ufw INPUT 链，`docker run -p` 的端口
ufw 管不住，要用 DOCKER-USER 链。
